# PowerFS AI Agent 规划（讨论稿 v0.1）

> 对齐 `powerfs-intro-outline.md` 第五部分「AI for Storage」（P24-P29）。
> 目标：让存储系统从"被动响应"走向"主动自治"，用 AI Agent 打通 **感知 → 决策 → 执行 → 验证** 闭环。
> 本文档为讨论稿，定稿后作为 powerfs-agent 模块的设计基线。

---

## 1. 背景与目标

### 1.1 为什么需要 Agent

第五部分定义了三条智能化主线（P24）：

| 主线 | 内容（P25-P27） | 现状 |
|---|---|---|
| 数据生命周期 | 热/温/冷自适应分层、EC/副本动态选择、WORM+回收站联动、冷数据归档淘汰 | 迁移/分层决策已沉淀在 Allocator（`LoadBalancer::analyze`），但触发靠手动或固定阈值 |
| 可靠性运维 | Bitrot 主动校验+自愈、盘位/节点劣化预测、告警收敛与根因定位 | Bitrot scrub 已可手动触发；AlertEngine 只做规则告警，无收敛、无根因 |
| 访问轨迹优化 | IoProfile 采集 → 指纹建模 → 在线自适应调参 → ML 预测预取 | IoProfile 采集已有，指纹与策略匹配尚未闭环 |

三条主线的共同缺口：**每一环都有"感知"和"执行"，缺一个"决策大脑"把环闭合**。AI Agent 就是这个大脑。

### 1.2 Agent 的定位

```
┌─────────────────────────────────────────────────────┐
│                    管理面（异步/慢速）                 │
│                                                     │
│   前端 UI ──► Monitor ◄──► powerfs-agent ◄──► LLM   │
│                │  ▲            │                    │
│        指标/告警│  │动作 API     │ 策略/决策           │
│                ▼  │            ▼                    │
│           Allocator（StatusQuery / ManagementApi）  │
├─────────────────────────────────────────────────────┤
│                    数据面（同步/快速）                 │
│   FUSE ──► Filer(Raft) ──► Volume(SPDK/EC/Bitrot)   │
│            （Agent 零侵入，数据路径不感知 Agent 存在）  │
└─────────────────────────────────────────────────────┘
```

核心定位：**Agent 是管理面的旁挂决策服务，不是数据面组件**。

- Agent 通过 Monitor 的既有 API 读取状态、触发动作（复用 RBAC/JWT 鉴权体系）
- Agent 通过 Allocator 已预留的 `StatusQuery`（只读）和 `ManagementApi`（写，支持 dry-run）做精细决策
- 数据路径（FUSE → Filer → Volume）完全不感知 Agent 存在，p99 不受影响

### 1.3 设计原则

1. **确定性优先**：能用规则/阈值表达的决策（分层迁移、scrub 调度）走策略引擎，毫秒级、可回放、可单测；LLM 只处理规则表达不了的部分（根因推理、跨域关联、自然语言交互、策略生成建议）。**不把 LLM 放进任何需要确定性保证的判断路径**。
2. **分级自治（L0-L3）**：Agent 的每个动作类别有独立自治级别，从"只观察"逐步放开到"自动执行+护栏"，任何时刻可一键降级回 L0。
3. **可审计、可回滚**：每个决策记录完整的 evidence（输入快照 → 推理依据 → 动作 → 结果验证），破坏性动作必须可回滚或有 dry-run 预演。
4. **复用而非重建**：指标、告警、拓扑、鉴权全部复用 Monitor；迁移/均衡执行复用 Allocator ManagementApi；Agent 不新建独立的数据通道。
5. **失败安全**：LLM 超时/不可用时，系统退化为纯规则引擎模式（即现状+固定阈值），不阻塞任何运维操作。

## 2. 总体架构

### 2.1 四层结构

```
┌────────────────────────────────────────────────────────────┐
│  L4 交互层    自然语言运维入口 / 前端面板嵌入 / 周报摘要        │
├────────────────────────────────────────────────────────────┤
│  L3 决策层    规则引擎(确定性) ─┐                            │
│               LLM 推理(根因/建议) ─┼─► 决策仲裁 ─► 任务编排    │
│               策略库(指纹匹配)  ─┘                            │
├────────────────────────────────────────────────────────────┤
│  L2 感知层    指标汇聚器 │ 事件订阅器 │ IoProfile 摄取 │ 快照   │
├────────────────────────────────────────────────────────────┤
│  L1 执行层    动作网关(分级审批/限流/审计) ─► Monitor API     │
│                                          ─► Allocator Mgmt │
└────────────────────────────────────────────────────────────┘
```

### 2.2 服务形态与部署

- 新增独立 crate `powerfs-agent`（Rust），独立进程部署，管理面组件之一
- 与 Monitor 同节点或独立节点部署均可；与 Monitor 通信走既有 HTTP API（JWT 服务账号）
- LLM 接入：OpenAI 兼容 API 抽象层，支持本地 vLLM（私有化）与云 API 两种后端，配置切换
- 状态存储：Agent 自身决策历史/审计日志存本地 RocksDB（或复用 Monitor 的存储），轻量无外部依赖

### 2.3 与现有组件的关系

| 组件 | Agent 对它的角色 | 说明 |
|---|---|---|
| Monitor | 主要数据源 + 动作通道 | 指标查询、告警事件、bitrot/迁移/balancer/conflicts 等 API 均已存在；需少量增补（见 §5） |
| Allocator | 决策依据 + 执行通道 | `StatusQuery` 读负载/容量/迁移任务；`ManagementApi` 写策略/触发迁移（dry-run 已预留） |
| Master | 拓扑事实来源 | 经 Monitor 代理读取 topology，不直连（遵循管理面交互原则） |
| Filer/Volume | 间接感知 | 通过 Monitor 汇聚的指标与 scrub 结果观察，不直接通信 |
| 前端 UI | 展示与人工审批入口 | Agent 建议/审批卡片嵌入现有前端；人机确认走 Monitor 鉴权 |

## 3. 三条主线的 Agent 化设计

### 3.1 生命周期 Agent（对齐 P25）

**目标**：热/温/冷分层、EC/副本选择、归档淘汰从"手动触发"到"轨迹驱动自动决策"。

决策流水线：

```
IoProfile 热度统计 ──► 温度分档 ──► 层级映射 ──► 迁移计划生成 ──► 护栏校验 ──► 执行/报批
     (L2 感知)        (规则)      (策略库)      (Allocator API)    (dry-run)    (分级)
```

- **温度模型（规则，确定性）**：基于 IoProfile 的访问频率/最近访问时间/读写比，滚动窗口计算 heat score，映射到 hot/warm/cold/archive 四档。阈值可配置，初始用静态阈值，后续由轨迹 Agent 反馈调优。
- **迁移计划（规则 + Allocator）**：温度分档变化生成迁移任务清单，先 dry-run 预演（容量、带宽、影响面），通过护栏后按 L2/L3 级别决定自动执行或报批。
- **EC/副本动态选择（规则 + 报批）**：数据降档到 cold/archive 时建议副本→EC 转换或更激进的 EC 配比；升档时反向建议。此类动作默认 L1（仅建议），因为涉及可靠性权衡。
- **WORM/回收站联动**：归档淘汰动作在 WORM 锁定对象上自动跳过；回收站清理纳入淘汰计划的最后一步，默认 L2。
- **容量规划（复用已有）**：Monitor 已有 capacity-projection 接口，Agent 周期性读取，预测 30/90 天容量耗尽风险，提前生成扩容建议（L1）。

### 3.2 可靠性 Agent（对齐 P26）

**目标**：告警风暴收敛、根因定位、主动自愈编排。

```
告警事件流 ──► 聚合去噪 ──► 根因推理 ──► 自愈剧本选择 ──► 护栏校验 ──► 执行/报批 ──► 验证闭环
  (Monitor)   (规则+拓扑)   (LLM 为主)    (SOP 知识库)     (dry-run)   (分级)     (动作后观测)
```

- **告警收敛（规则先行）**：同源告警（同节点/同盘/同 volume）时间窗内聚合；拓扑感知的传播抑制（下游节点告警被上游根因吸收，如交换机故障导致的批量失联）。规则能收敛 80% 常规风暴，剩余复杂案例进 LLM。
- **根因定位（LLM 为主、规则校验）**：将聚合后的告警集合 + 拓扑 + 最近变更（配置修改、迁移任务、scrub 状态）+ 指标曲线作为 context 交给 LLM，输出候选根因与置信度。LLM 输出必须附带 evidence 链，供人复核。
- **自愈剧本库（SOP）**：预定义可执行剧本，如：
  - 静默损坏 → 触发对应 volume 的 scrub + Auto Repair（已有 API）
  - 节点劣化（SMART/延迟趋势）→ 触发该节点数据迁出 + 置维护模式（Allocator ManagementApi 已预留"节点维护"接口）
  - Filer 脑裂/leader 异常 → 报告 + 建议 transfer-leader（已有 API，默认 L1 人工确认）
  - 容量水位 → 触发均衡检查（已有接口）
- **巡检（规则）**：周期性全集群体检（配置漂移、副本不足、scrub 积压、告警规则合理性），输出巡检报告。
- **验证闭环**：自愈动作执行后，Agent 继续观测相关指标 N 分钟，验证恢复；未恢复则升级处理（重新推理或升级报批）。

### 3.3 轨迹优化 Agent（对齐 P27）

**目标**：把 IoProfile 采集数据变成可执行的调优动作，按三阶段递进。

| 阶段 | Agent 能力 | 依赖 |
|---|---|---|
| 阶段 1：离线指纹 | 批量摄取 IoProfile trace → 生成工作负载指纹 → 匹配预定义策略库（预取窗口/lease TTL/cache 参数）→ 输出参数建议 | IoProfile 采集已有；需定义指纹特征向量和策略 DSL |
| 阶段 2：在线自适应 | 运行时检测负载模式切换（如批量训练加载 → 小文件随机读）→ 动态下发参数调整到 FUSE/Filer（经既有配置通道）| 需指纹实时计算 + 参数热更新通道 |
| 阶段 3：ML 预测 | 预测未来访问模式（数据集预加载预取、checkpoint 时机预测），前瞻性调参 | 研究探索，依赖阶段 1/2 数据积累 |

- **指纹建模**：特征向量建议包含：I/O 大小分布、读写比、顺序度、随机度、打开/关闭频率、目录深度、并发度、时间模式（周期性检测）。指纹 = 特征向量哈希/聚类结果，映射到策略条目。
- **策略 DSL**：`条件(指纹/指标) → 动作(参数调整/迁移/告警)` 的声明式规则（YAML/TOML），动作白名单制；可由人编写，LLM 可生成草稿（人工审核后入库）。
- **调优动作落点**：预取参数、lease TTL、cache 容量、coalescer 配置（Monitor 已有 coalescer/circuit-breaker 配置 API）。
- **IoProfile × InodeInfo 结合与低开销采集**：见 §4.5。

### 3.4 三主线协同（对齐 P28）

- 轨迹 → 生命周期：热度分档直接驱动分层迁移（3.1 的输入即来自 IoProfile）
- 生命周期 → 可靠性：层级/EC 变化触发冗余复核，scrub 计划按数据温度分层调度（冷数据 scrub 优先级低）
- 可靠性 → 轨迹/生命周期：故障预测事件修正热度模型（劣化盘上的"热数据"不再计入正常热度），迁移计划避开劣化节点

三主线共享同一套感知层数据和执行层通道，决策层各管一域、交叉处仲裁（见 §4.4）。

## 4. 关键机制设计

### 4.1 感知层：数据源与事件流

| 数据源 | 通道 | 用途 |
|---|---|---|
| 集群/节点/volume 指标 | Monitor API 轮询（已有） | 温度模型、容量预测、巡检 |
| 告警事件 | Monitor 告警推送（需新增 SSE/Webhook，见 §5） | 可靠性 Agent 触发源 |
| IoProfile 热度统计 | FUSE 端在线聚合 → 批量上报（§4.5，待实现） | 指纹建模、热度分档 |
| Bitrot scrub 结果 | Monitor API（已有） | 自愈触发源 |
| 拓扑 | Monitor /api/topology（已有） | 根因定位的拓扑关联 |
| 迁移/均衡任务状态 | Allocator StatusQuery（已预留） | 避让与验证 |

### 4.2 决策层：双引擎 + 仲裁

- **规则引擎**：策略 DSL 驱动，覆盖阈值类、聚合类、剧本类决策；版本化、可单测、可灰度。
- **LLM 推理**：三类任务——根因分析（输入告警+拓扑+变更，输出候选根因）、建议生成（巡检报告摘要、容量规划建议）、策略草稿生成（人工审核入库）。统一走 OpenAI 兼容接口，支持本地/云后端。
- **仲裁器**：同一对象上多个决策冲突时的优先级：可靠性动作 > 生命周期迁移 > 轨迹调优；LLM 建议与规则结论冲突时默认采信规则（LLM 仅在其无规则覆盖的领域生效）。

### 4.3 执行层：动作网关与分级自治

所有 Agent 动作必须经过动作网关，禁止旁路直连：

**自治级别定义**：

| 级别 | 行为 | 适用动作举例 |
|---|---|---|
| L0 观察 | 只读，产出报告 | 巡检、指纹分析、周报 |
| L1 建议 | 生成建议卡片，人工点击采纳 | 扩容建议、EC 调整、transfer-leader |
| L2 报批执行 | dry-run 预演 + 生成执行计划，人工一键批准 | 分层迁移批次、scrub 触发 |
| L3 自动+护栏 | 自动执行，护栏约束内 | 温度明确的冷数据迁移、告警去噪、参数微调 |

**护栏（Guardrails，硬编码，不受 LLM 影响）**：

- 影响面预算：同时在途迁移任务数上限、单批数据量上限、带宽上限（避免影响在线 I/O）
- 时间窗：可配置维护时间窗外的动作自动降级为 L1
- 保护名单：WORM 锁定对象、当前有活跃 lease 的文件、leader 节点等强制豁免
- 速率与回滚：每类动作单位时间执行上限；破坏性动作必须预登记回滚方案
- 全局开关：`/api/agent/config` 一键将全部动作降级 L0（紧急止血）

**审计**：每个动作记录五元组（触发源、输入快照、推理依据、动作与参数、验证结果），不可篡改，前端可查。

### 4.4 失败安全与降级

- LLM 不可用 → 规则引擎独立工作（等同现状能力 + 固定阈值），Agent 服务不阻塞系统
- Monitor 不可达 → Agent 进入只读降级，本地缓存最后快照，恢复后增量补齐
- 决策效果回归 → 每类 L3 动作有效果指标（如迁移后命中率、告警后 MTTR），连续劣化自动回滚并降级该类动作

### 4.5 IoProfile × InodeInfo 结合与低开销采集设计

现状：IoProfile 尚未实现（io-profile-adaptive-optimization-plan.md 规划为 `powerfs-profiler` 独立 crate + FUSE hook，默认关闭）；Filer 端 `InodeInfo`（shard_store.rs）已含 `atime/mtime/size/file_type/storage_mode/reliability`，随 Raft 持久化。

**结合原则：读取时 join，不在存储上合并。**

- 热度统计数据（HeatStat）作为旁路表按 inode 关联，**不向 `InodeInfo` 增加任何字段**——避免每 inode 元数据膨胀，更重要的是热度写入不进 Raft（热度是统计信号不是元数据事实，进 Raft 会造成读写放大，违反"Filer 只对 dirty/deleted 写 Raft"的既有约束）
- 生命周期决策时 join：`HeatStat(热度) × InodeInfo(file_type/size/storage_mode/reliability)` → 分层/EC 决策；决策产生的变更（storage_mode/reliability 修改）才走既有 Raft 路径
- `InodeInfo.atime` 保留为兜底信号（HeatStat 缺失/丢失时的降级热度来源）

**低开销采集（FUSE 端，四层削减）**：

1. **事件层：无锁采样**。hook 内只做一次原子计数递增（纳秒级）；详细字段（offset/duration/timing）按 1/N 采样记录（默认 N=64），未命中采样的访问只 +1 计数。ring buffer per-thread 缓冲，无锁竞争。
2. **聚合层：在线归约，不存全量 trace**。后台线程将事件归约为 per-inode `HeatStat`（紧凑布局 ~64B）：

   ```
   HeatStat（~64B）:
     inode: u64
     last_access_s: u32        // 相对时间戳（秒）
     read_cnt / write_cnt: u32 // 饱和计数
     read_bytes / write_bytes: u64
     size_buckets: [u32; 4]    // <4K / 4K-64K / 64K-1M / >1M
     seq_ratio: u8             // 顺序度 0-255
     flags: u8                 // 读多/写多/元数据密集等标记位
   ```

3. **内存层：活跃集控制**。只对窗口内访问过的 inode 维护 HeatStat，LRU 淘汰；淘汰前将最终值批量 flush 到上报通道。内存上限 = 活跃 inode 数 × 64B（百万活跃 inode ≈ 64MB，可配置上限强制驱逐）。
4. **传输/存储层：批量上报 + 降采样**。FUSE 每 N 秒/M 条批量上报 HeatStat 增量（SSE 反向不通，走 HTTP batch push 到 Agent）；Agent 侧按 5min → 1h → 1d 三级降采样落 RocksDB（非 Raft），原始 5min 粒度保留 7 天。

**空间与性能账**：

- 每 inode 长期占用 ≈ 64B（当前值）+ ~100B（三级降采样历史）≈ 200B；1 亿 inode ≈ 20GB，且可按 bucket/目录 TTL 清理
- 在线 I/O 路径新增开销：1 次原子递增 + 偶发 memcpy，无锁、无 RPC、无 Raft；p99 不受影响
- 默认关闭，Monitor/Agent 下发配置开启（复用既有"可插拔、默认关闭"原则）

**上报通道**：FUSE → Agent 直连 HTTP batch push（Agent 有服务账号，经 Monitor 鉴权体系签发 token）；Agent 不可达时 FUSE 端本地聚合继续、环形覆盖旧数据（采集层永远不阻塞 I/O）。

## 5. 需要新增/增补的接口（增量清单）

> 接口契约已冻结为独立文档：`docs/agent-api-contract.md`（Step 0 前后端并行开发依据）。

| # | 增量 | 提供方 | 说明 |
|---|---|---|---|
| 1 | 告警事件推送（SSE） | Monitor | 已定 SSE；现在只能轮询 `/api/alerts`，Agent 与前端共用事件流 |

## 6. 实施路线（对齐 P29/P30 三阶段）

### Step 0：Mock 驱动前端演示（先行，内功能后置）
- **目标**：用 Mock 数据先把前端演示搭起来，内部功能完善放在后续步骤
- powerfs-agent 服务骨架：只提供 Mock 模式——模拟指标快照、告警流、建议卡片（分层迁移/扩容/根因）、决策历史、巡检报告
- Mock 数据生成器：可配置场景（告警风暴、容量告急、冷数据堆积），演示可重复
- 前端：建议卡片组件、审批流交互、Agent 决策历史页、Agent 面板入口——全部走 `/api/agent/*` 接口契约（真实后端后续替换 Mock 实现即可，接口先行冻结）
- **验收**：端到端演示"告警产生 → Agent 建议卡片 → 人工批准 → 决策留痕"，全程 Mock 数据

### M0：只读诊断 MVP（验证数据链路）
- powerfs-agent crate 骨架 + 感知层（轮询 Monitor 全部指标/告警/scrub/topology），Mock 数据源替换为真实数据源
- 规则引擎 + 巡检报告 + 周报（L0）
- 审计日志与决策记录基础设施
- **验收**：Agent 定期产出巡检报告，前端可查看

### M1：可靠性 Agent（最先产生价值）
- 告警事件订阅（SSE）+ 聚合去噪（规则）+ 根因推理（LLM，双后端）+ 建议（L1）
- 自愈剧本库 v1：bitrot→scrub、容量→均衡检查（L2 报批）
- **验收**：告警风暴场景下收敛率可量化，根因建议准确率人工评估

### M2：生命周期 Agent
